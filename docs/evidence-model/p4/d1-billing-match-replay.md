## 1. The question

`visa_10_4_fraud.criticalCategories` is:

```ts
criticalCategories: ["payment_authentication", "billing_match"],
```

`billing_match` is a declared `EvidenceFactCategory` with **zero members**. PR-C4 (C-14,
2026-08-09) retired `billing_address_match`, the only field key that mapped to it, through the
`retiredKeys.ts` boundary; `categoryForField` no longer returns `billing_match` for any field, and
`tests/unit/retiredFieldKeyContainment.test.ts` pins that.

`derivePackageMode` requires **every** critical category to be present among the approved facts'
categories. A category with no members can never be present. **Therefore every Visa 10.4 package is
already `narrow`, unconditionally** — the `payment_authentication` half of the pair, the fact-count
rule, the strength rule and the fatal-loss rule are all dead code for this module today.

Removing the entry restores the conditional behaviour and flips real packages `narrow → full`.
`packageMode` is bank-visible in effect: it selects thesis templates
(`ThesisTemplate.packageMode`) and gates the narrow-mode aggressive-phrasing rules
(`NARROW_AGGRESSIVE_PHRASES` in `validateNarrative.ts`), so a package that flips to `full` argues
differently to the same issuer.

---

## 2. Method, and why it is exhaustive rather than sampled

`derivePackageMode`'s answer is a function of exactly five booleans:

| Input | Source |
|---|---|
| case strength ∈ {strong, moderate, weak, insufficient} | `CaseAssessment` |
| fatal-loss triggered | `lib/automation/fatalLoss.ts` |
| ≥2 distinct approved fact categories | approved fact set |
| `payment_authentication` present | approved fact set |
| `billing_match` present | approved fact set — **always false today** |

That is 64 cells, of which **32 are reachable** (the 32 with `billing_match` present are not
reachable — see §5). The replay enumerates all 32 through the **real** `derivePackageMode`, with
the module exactly as it ships and with the counterfactual module that drops the entry. A
re-implementation would have measured the re-implementation, so `derivePackageMode` was exported
from `factClassifier.ts` for this purpose and production callers still reach it only through
`classifyFacts`.

**What this method cannot give, and why.** Per-package population counts — "N of the 61 open
unsubmitted packages sit in a transitioning cell". Agent B's worktree has no Supabase link, and the
epic's hard constraints forbid creating one; the CP-0 census (§4) is the recorded population and the
coordinator can re-run the per-package count against it with a single read-only query before PR 2's
review. The cell enumeration below is complete and does not change with that count: it says
*which* cases move, the count would say *how many*.

## 5. The one reachability caveat

`billing_match` is unreachable from the collector path, but it is **not structurally impossible**.
`factClassifier` promotes manual evidence with `category: m.evidenceCategory ?? "manual_evidence"`,
and `defence_manual_evidence.evidence_category` accepts any `EvidenceFactCategory` — including
`billing_match` — as an ops override. Prod holds **zero** `defence_manual_evidence` rows (C-7), so
no such fact exists today.

This matters only if D-1 is answered **keep**: the entry would then be a dormant switch that a
single ops row could flip, moving a Visa 10.4 package from `narrow` to `full` with no code change
and no review. The harness pins that behaviour so the answer is made with it visible.

## 7. THE DECISION — KEEP (maintainer, 2026-08-10)

`billing_match` **stays** in `visa_10_4_fraud.criticalCategories` for this delivery.

### 7.1 Why

**Preservation of approved production behaviour.** Two facts, together:

1. Removal changes the bank narrative of **61 currently-live open cases** (§4a). `packageMode`
   selects thesis templates and gates the narrow-mode phrasing rules, so those 61 cases would
   start arguing differently to the same issuers. That is a real change to filed evidence, and it
   has not been reviewed as one.
2. **`derivePackageMode` sits on the SHARED classification path, not behind the canonical
   switch.** It is reached by `buildDefencePackageJob` regardless of `CANONICAL_PIPELINE`, so
   removing the entry would take effect **immediately, on the activation-OFF route** — not at
   PR 3 with the rest of the cutover, and not with the rollback story the switch provides.

A behavioural change to 61 live cases that lands outside the switch it appears to belong to is
the opposite of what a dark PR is for. The entry is orphaned; it is also, today, load-bearing for
behaviour that is approved and in production.

### 7.2 What is NOT being done

- No edit to `visa_10_4_fraud.ts`.
- **No containment fix.** No CI invariant, no guard, no shim, no second predicate to "protect"
  the entry or to route around it. The entry is correct-as-shipped for this delivery; adding
  machinery to defend a decision to change nothing would be a third layer with an opinion about
  `packageMode`, which is the class of problem this epic exists to close.

### 7.3 What is carried to backlog

Two concerns are real and are **deferred, not dismissed** — recorded in
`docs/plans/canonical-pipeline-lite.plan.md` §14:

1. **The orphaned category itself.** `billing_match` has zero members since PR-C4 retired
   `billing_address_match`, so the `payment_authentication` half of the pair, the fact-count rule,
   the strength rule and the fatal-loss rule are all unreachable for this module. Visa 10.4 is the
   only reason module that has never produced a full-mode package (§4a). Whether that is the right
   argument posture for 10.4 is a question about the module, to be answered on its own evidence
   after the cutover — not as a side effect of a category retirement.
2. **The manual-override reachability caveat (§5).** While the entry is kept, a single
   `defence_manual_evidence` row categorised `billing_match` would flip a Visa 10.4 package from
   `narrow` to `full` with no code change and no review. Prod holds zero such rows (C-7), so
   nothing is exposed today. Post-cutover work decides whether that override should be
   constrained.

Neither is a blocker for PR 2 or PR 3.
